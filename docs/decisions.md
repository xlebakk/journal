# Журнал решений

Формат: дата · решение · почему. Новые записи — снизу.

## Этап 0

Предварительные ответы на вопросы о модели данных и правах. Пользователь ответил «продолжи», поэтому приняты рекомендованные варианты. Каждый можно пересмотреть до этапа, на котором он реализуется.

- 2026-11-21 · Первичные ключи всех сущностей, видимых через API, — UUID (v4). · Второй слой защиты от IDOR поверх `for_user()` → 404: ID нельзя перебрать, и по ним не видно, сколько в системе объектов. Сменить тип ключа потом дорого.
- 2026-11-21 · Роли хранятся массивом `roles` в `User` с CHECK-ограничением «`student` ни с чем не совмещается»; история изменений ролей — только в аудите. · Просто и быстро в запросах; отдельная таблица назначений нужна, только если понадобятся периоды действия ролей.
- 2026-11-21 · Будущая роль `parent` совместима с `teacher`/`admin`, но не со `student`; у ребёнка может быть несколько аккаунтов родителей (`ParentLink`). · Сотрудник центра может быть родителем ученика.
- 2026-11-21 · Шкала оценок хранится в `AcademicYear`, в `Settings` — только шкала по умолчанию для новых годов. Оценки — целые числа. · Правило 11: шкала фиксируется для года, в котором есть оценки. Дробных баллов в ТЗ по умолчанию нет.
- 2026-11-21 · Все администраторы равны. Нельзя снять роль `admin` с себя или с последнего активного администратора и нельзя архивировать себя. · Нельзя случайно остаться без администратора.
- 2026-11-21 · 2FA и тайм-ауты сессии определяются самой строгой ролью аккаунта, а не активной. · Иначе переключение на роль преподавателя обходит обязательную 2FA и 30-минутный тайм-аут администратора.
- 2026-11-21 · Преподаватель видит только свой предмет. Ушедших из группы учеников он видит в своём курсе за период их членства. `TeacherNote` видят только автор и администратор. · SPEC §7: «карточка ученика по своему предмету».
- 2026-11-21 · Ученик не видит других учеников нигде, даже имён одногруппников. · SPEC §6: данные других учеников недоступны нигде.
- 2026-11-21 · **Открыто:** права ассистентов курса (`Course.assistants`). Решить до этапа 2.

Технические решения:

- 2026-11-21 · Django 5.2 LTS, Python 3.13. · Актуальная LTS (поддержка до апреля 2028); 3.13 поддерживается 5.2.
- 2026-11-21 · Пакетный менеджер бэкенда — uv, lock-файл `backend/uv.lock`. · Быстрый, воспроизводимый, сам ставит нужную версию Python.
- 2026-11-21 · Фронтенд — npm с `--save-exact`, lock-файл `package-lock.json`. · Уже установлен вместе с Node, отдельный менеджер не нужен.
- 2026-11-21 · `AUTH_USER_MODEL = accounts.User` заложен на этапе 0 в минимальном виде (UUID, login, ФИО, is_active). · Модель пользователя почти невозможно сменить после первой миграции; поля этапа 1 добавятся миграциями.
- 2026-11-21 · Логин уникален без учёта регистра: хранится в нижнем регистре плюс уникальный индекс по `Lower(login)`. Логин архивированного пользователя остаётся занятым навсегда. · Аудит и печатные карточки однозначно указывают на человека.
- 2026-11-21 · Встроенная админка Django не подключена ни в dev, ни в prod. · У администратора свой интерфейс (SPEC §8); меньше поверхность атаки.
- 2026-11-21 · Анонимный запрос к API получает 401: свой `SessionAuthentication` возвращает заголовок `WWW-Authenticate`. · DRF без этого отвечает 403, а SPEC §15 требует 401.
- 2026-11-21 · В тестах кэш — `LocMemCache`, база — настоящий PostgreSQL. · Тесты изолированы и не требуют Redis. Логика лимитов использует только API кэша Django, которое одинаково у обоих бэкендов. Ограничения и триггеры БД должны совпадать с продом, поэтому база настоящая.
- 2026-11-21 · Переменные БД приложения называются `DB_*`, а не `POSTGRES_*`. · `POSTGRES_*` читает образ postgres для суперпользователя; разные имена исключают путаницу ролей.
- 2026-11-21 · В dev приложение подключается к БД как `journal` (NOSUPERUSER, CREATEDB — для тестовой базы); суперпользователь `postgres` нужен только для инициализации контейнера. · SPEC §11: приложение не должно уметь обойти триггер аудита.
- 2026-11-21 · Шрифты — пакеты `@fontsource/*` (Literata 600, Golos Text 400/500/600, JetBrains Mono 500/700). · OFL, есть кириллица; Vite кладёт woff2 в бандл, то есть шрифты отдаёт свой сервер без CDN. Браузер грузит только нужные subset-ы по `unicode-range`.
- 2026-11-21 · `lucide-react` — иконки. · Указан в ТЗ; импортируются поштучно, лишнее отсекает tree-shaking.
- 2026-11-21 · `@tanstack/react-query`, `react-router` — указаны в ТЗ. Radix UI подключается на этапе 1 вместе с первым меню и диалогом.
- 2026-11-21 · ESLint 9, а не 10. · `eslint-plugin-jsx-a11y` пока не поддерживает ESLint 10, а проверки доступности важнее новой версии линтера.
- 2026-11-21 · `eslint-plugin-jsx-a11y` (strict) — линтер доступности. · WCAG 2.2 AA (SPEC §12) проще держать, когда нарушения ловятся при написании кода.
- 2026-11-21 · Свой мини-i18n (`shared/i18n`, функция `t()` с типизированными ключами) вместо i18next. · Пока язык один; второй язык — ещё один JSON и выбор словаря. Ноль зависимостей.
- 2026-11-21 · Токен `--pencil` в светлой теме: `#8A5A0C` вместо `#A86F12` из ТЗ. · Исходный цвет даёт контраст 4,06 на `--sheet` и 3,76 на `--paper` — ниже AA (4,5) для «оп» шрифтом 15 px. Тон тот же, только темнее.
- 2026-11-21 · Добавлен токен `--marker-soft` (светлая тема — 40% маркера, тёмная — 12%) для тела колонки сегодняшнего дня; полный `--marker` — для заголовка дня и совпадений поиска. · Красное «н» на полном маркере в тёмной теме даёт контраст ниже AA. Скрипт контраста проверяет обе пары.
- 2026-11-21 · Пример даты в ТЗ «21.11.2026 · пятница» — опечатка: 21.11.2026 — суббота. Тесты используют пятницу 20.11.2026. · День недели считает `Intl` в поясе центра.
- 2026-11-21 · Стайлгайд подключается через `import.meta.env.DEV` и ленивый импорт; CI проверяет, что его нет в `dist`. · SPEC §12: «только в dev».
- 2026-11-21 · Сборка Vite с `assetsInlineLimit: 0`. · Никаких `data:`-шрифтов и inline-ресурсов — CSP остаётся строгой.
- 2026-11-21 · CI — GitHub Actions, обновления зависимостей — Dependabot (uv, npm, docker, actions). · Указано в ТЗ. Удалённого репозитория пока нет: CI заработает после push на GitHub.

## Этап 1

- 2026-11-21 · Зависимости: `pyotp` (TOTP), `cryptography` (Fernet для секретов TOTP), `segno` (QR в SVG на сервере, без зависимостей). · Указаны в ТЗ или минимальны; QR как data:-URI проходит строгую CSP (`img-src 'self' data:`).
- 2026-11-21 · Фронтенд: `@radix-ui/react-dropdown-menu`, `@radix-ui/react-dialog`, `react-hook-form`, `zod`, `@hookform/resolvers` — из ТЗ; `openapi-typescript` — типы из OpenAPI; `@playwright/test` — e2e. Выпадающие списки — нативный `<select>`, а не Radix Select: доступен везде и не требует порталов. · Минимум кода и полная доступность.
- 2026-11-21 · `openapi-typescript` объявляет peer `typescript@^5`, в проекте TS 6: в `package.json` стоит `overrides`, генератор использует TS проекта. · TS нужен ему только для печати кода; типы генерируются корректно, проверено в CI сравнением с закоммиченным файлом.
- 2026-11-21 · Ответы API об ошибках — машинные коды `{"detail": "<code>"}` (и `{"поле": ["<code>"]}` для валидации); перевод на русский — во фронтенде (`errors.*` в `ru.json`). · Тексты в одном месте и готовы ко второму языку.
- 2026-11-21 · Вход: GET `/auth/login` отдаёт название центра и контакты и ставит CSRF-cookie; POST проверяет CSRF и для анонимов (DRF этого не делает). Шаг TOTP — отдельный публичный эндпоинт `/auth/totp`. · Страница входа — единственная публичная; без CSRF на входе возможна «подмена входа» (login CSRF).
- 2026-11-21 · Неверный пароль, несуществующий и отключённый логин дают один и тот же ответ `400 invalid_credentials`; для несуществующего логина проверяется хэш-пустышка Argon2. Блокировка хранится по строке логина, поэтому и несуществующие логины блокируются одинаково. · SPEC §11: ответ и время одинаковы.
- 2026-11-21 · Пятая неудачная попытка ставит блокировку, шестая получает 429. Повторные блокировки удваиваются: 15 → 30 → … → 24 ч; уровень эскалации живёт 48 ч. Успешный вход сбрасывает счётчик неудач, но не уровень. · SPEC §2 и §15 («6-я попытка → 429»).
- 2026-11-21 · 5 неверных TOTP-кодов подряд обнуляют незавершённый вход и считаются неудачной попыткой для блокировки логина. Код нельзя использовать повторно: запоминается последний принятый 30-секундный шаг. · Лимит попыток на ввод кода из SPEC §11 и защита от перехвата кода.
- 2026-11-21 · Резервные коды хранятся как HMAC-SHA256 (`salted_hmac` с SECRET_KEY), а не Argon2. · У кода около 40 бит случайности, перебор ограничен лимитами; HMAC делает проверку 10 кодов мгновенной.
- 2026-11-21 · Сессии — в Redis (cache backend), плюс запись `UserSession` в PostgreSQL для списка сеансов и отзыва. Middleware на каждом запросе проверяет, что запись активна: отзыв, тайм-аут, блокировка, смена ролей завершают сеанс сразу. · Отзыв не требует знать ключ сессии в Redis; в базе хранится только SHA-256 ключа.
- 2026-11-21 · Без «Запомнить устройство» cookie живёт до закрытия браузера, абсолютный срок проверяет сервер. С ним — постоянная cookie: 14 дней (преподаватель), 30 дней (ученик), без тайм-аута бездействия. Для администратора флажок не действует. · SPEC §2.
- 2026-11-21 · Права проверяются по *активной* роли сессии: директор в роли преподавателя не попадает в админские эндпоинты. Тайм-ауты и 2FA — по самой строгой роли аккаунта (решение этапа 0). · Переключение роли явное; сессия при нём получает новый id.
- 2026-11-21 · Повторный ввод пароля (5 минут) требуется для смены ролей, сброса 2FA, выключения своей 2FA и выпуска новых резервных кодов. Вход сам по себе считается вводом пароля. · SPEC §8 «опасные действия»; остальные пункты списка (массовая архивация, шкала, экспорт) появятся на своих этапах.
- 2026-11-21 · Неверный пароль при смене пароля и повторном вводе засчитывается в блокировку логина. · Иначе украденная сессия позволила бы подбирать пароль без лимита.
- 2026-11-21 · «Блокировка» администратором = `is_active=False` (обратимо); «архив» = `archived_at` + `is_active=False` (обратного действия в первой версии нет). Себя и последнего активного администратора нельзя заблокировать, архивировать и лишить роли admin. · SPEC §8, §10.10 и решение этапа 0.
- 2026-11-21 · Смена ролей пользователя завершает все его сеансы. · Права в открытых сессиях не должны пережить изменение ролей.
- 2026-11-21 · Роль `parent` и `ParentLink` есть в модели, но через API назначить её пока нельзя (`unknown_role`). · SPEC §16: заложить, но не делать.
- 2026-11-21 · «Примерное место по IP» в списке сеансов не показывается, только IP. · Нужна база GeoIP с отдельной лицензией; вернёмся к этому вместе с мониторингом на этапе 7.
- 2026-11-21 · База PostgreSQL создаётся с ICU-локалью (`--locale-provider=icu --icu-locale=und`) в compose и CI. · В локали `C` `UPPER()` не трогает кириллицу, и поиск «алиев» не находил «Алиев»; тест поиска это ловит.
- 2026-11-21 · **Известное ограничение до этапа 7:** приложение и миграции работают под одной ролью БД, владельцем таблиц. Владелец может отключить триггер аудита. На этапе 7 миграции пойдут под ролью-владельцем, а приложение — под отдельной ролью только с DML-правами и без UPDATE/DELETE на `audit_auditlog`. · Триггер уже защищает от ошибок приложения; разделение ролей — инфраструктура продакшена.
- 2026-11-21 · `seed_demo` на этапе 1 создаёт только людей (1 администратор, 6 преподавателей, 60 учеников) с `must_change_password=False` для удобства демо; администратор при первом входе настраивает 2FA. Группы и занятия добавятся на этапах 2–3. · Моделей групп и занятий ещё нет.
- 2026-11-21 · e2e (Playwright) идут на отдельной базе `journal_e2e`, которую `seed_e2e` пересоздаёт целиком (DROP SCHEMA). Команда отказывается работать с любой другой базой и вне DEBUG. · Строки аудита нельзя удалить (триггер), поэтому чистое состояние — только пересозданием схемы.

## Этап 2

- 2026-11-21 · Ассистенты курса имеют права преподавателя этого курса: состав, журнал, посещаемость, оценки, темы, расписание. Пробные тесты они не создают и чужих заметок об учениках не видят. · Ответ пользователя перед этапом 2. В расписании ассистент видит занятия курса (`Lesson.objects.for_user`).
- 2026-11-21 · Перенос занятия — та же запись `Lesson`: меняются `date/start_time/end_time/room`, исходные значения шаблона хранятся в `planned_*`. · Ответ пользователя. Всё, что привязано к занятию (оценки и посещаемость на этапе 3), остаётся на месте; пометка «перенесено с …» берётся из `planned_*`.
- 2026-11-21 · Дата и время занятия — гражданские дата и время на часах центра (`DateField` + `TimeField`), а не метка времени UTC. · Занятие «в 14:00» остаётся в 14:00; «сегодня» считается через `timezone.localdate()` (SPEC §2).
- 2026-11-21 · Генерация идемпотентна за счёт уникального ключа `(slot, planned_date)`: перенесённое или отменённое занятие не создаётся заново. Окно — 28 дней от «сегодня». Занятия не создаются в нерабочие дни, вне учебного года, вне периода слота и для архивных групп. · SPEC §9, §15.
- 2026-11-21 · Изменение шаблона затрагивает только будущие (с сегодняшнего дня) запланированные занятия, которые никто не трогал руками. «Тронутое» занятие — перенесённое, с заменой, сменой кабинета, отменой или заполненной темой/ДЗ — остаётся как есть. Если что-то меняется или удаляется, PATCH без `confirm: true` отвечает 409 `confirmation_required` с планом по датам; `POST /admin/slots/{id}/preview` показывает план, ничего не сохраняя. · SPEC §9: «после подтверждения со списком затронутых дат».
- 2026-11-21 · При удалении слота будущие нетронутые занятия удаляются, а прошлые и исключения остаются и отвязываются от слота. · История не теряется, а ключ генерации больше не нужен.
- 2026-11-21 · Пересечение по преподавателю, кабинету или группе блокирует сохранение: 409 `schedule_conflict` со списком. Ученик сразу в двух группах и нехватка мест в кабинете — только предупреждение в ответе. Конфликты проверяются для слотов (тот же день недели и пересекающиеся периоды) и для конкретных занятий. Отменённые занятия не мешают, ассистенты в проверку не входят. · SPEC §9.
- 2026-11-21 · Новый нерабочий день удаляет нетронутые сгенерированные занятия этого дня; удаление нерабочего дня создаёт их снова. Архивация группы удаляет её будущие нетронутые занятия. При смене преподавателя курса будущие запланированные занятия переходят к новому, кроме замен. · Расписание не должно противоречить справочникам.
- 2026-11-21 · Оптимистичная блокировка (SPEC §10.12) уже работает на исключениях: каждый запрос несёт `version`, при несовпадении — 409 `version_conflict`; строка блокируется `SELECT … FOR UPDATE`. · Тот же механизм получит журнал на этапе 3.
- 2026-11-21 · Запрос преподавателя на отмену или перенос (`ScheduleRequest`) — не больше одного ожидающего на занятие. Одобрение администратором применяет изменение с той же проверкой конфликтов. · SPEC §9.
- 2026-11-21 · Пересечения периодов (учебные годы, модули года, членство ученика в группе) запрещены exclusion-ограничениями PostgreSQL (`btree_gist`); один текущий год — частичный уникальный индекс. · Корректность на уровне БД, а не только в коде. `btree_gist` — доверенное расширение: владелец базы ставит его без суперпользователя.
- 2026-11-21 · Уникальность проверяет база. Сериалайзеры наследуют `DatabaseUniqueModelSerializer`, который убирает автоматические валидаторы DRF: они отвечают переведёнными фразами и ошибаются на частичных индексах (один текущий год). Нарушение ограничения превращается в код по имени ограничения (`AuditedAdminViewSet.constraint_codes`). · Ошибки API — только коды.
- 2026-11-21 · Все административные справочники и структура идут через `AuditedAdminViewSet`: создание, изменение и удаление пишутся в аудит в той же транзакции. Удаление используемой записи — 409 `in_use`, вместо него архив. · SPEC §10.8.
- 2026-11-21 · UUID и даты в query-параметрах разбираются строго (`core/params.py`): мусор даёт 400, а не 500. · Найдено при написании фильтров расписания.
- 2026-11-21 · Расписание недели на компьютере — разлинованная таблица «время начала × дни», а не сетка с позиционированием по минутам. Занятия разных групп в одно время стоят в одной ячейке, на телефоне — список по дням. · Сетке с абсолютным позиционированием нужны inline-стили, а их запрещает CSP (`style-src 'self'`). - 2026-11-21 · Печать расписания группы — кнопка «распечатать» в расписании администратора с фильтром по группе, CSS `@page A4 landscape`. · SPEC §9, без PDF-библиотек (SPEC §3).
