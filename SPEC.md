## Как пользоваться этим промтом

Этот раздел — для тебя. Всё, что ниже, — сам промт для Claude Code: его не нужно пересказывать, его нужно положить в проект целиком.

1. Создай пустую папку проекта (например, `journal/`) и сделай в ней `git init`.
2. Экспортируй этот документ в Markdown и сохрани в корень папки как `SPEC.md`.
3. Пройди таблицу «Параметры по умолчанию» и поправь то, что знаешь (название центра, шкала оценок, часовой пояс). Остальное можно оставить.
4. Запусти Claude Code в этой папке и отправь первое сообщение:

```
Прочитай SPEC.md целиком. Составь план этапа 0 и этапа 1, задай вопросы по тому,
что неоднозначно и трудно переделать потом (модель данных, права доступа).
После моего ответа реализуй этап 0, затем остановись и покажи результат.
```

5. Дальше иди по этапам: один этап — одна ветка и отдельная сессия. Не проси сделать всё сразу: на большом объёме модель начинает срезать углы именно в безопасности и тестах.
6. После каждого этапа сам зайди под тремя ролями (демо-данные создаются командой `seed_demo`) и проверь, что ученик не видит чужого, а преподаватель — чужих групп.

## 1. Контекст и цель

Ты — ведущий full-stack разработчик. Построй электронный журнал для учебного центра, который готовит школьников к поступлению в вузы. Система хранит группы, учеников, расписание, оценки, посещаемость, темы занятий и результаты пробных тестов и показывает каждой роли только её часть.

Пользователи и что они делают:

- **Администратор** (1–3 человека) — заводит людей, группы, предметы и расписание, следит за заполнением журналов, строит отчёты, смотрит аудит.
- **Преподаватель** — по своим предметам в своих группах отмечает посещаемость, ставит оценки, записывает дату, тему, вид занятия и домашнее задание, вносит результаты пробных тестов.
- **Ученик** — смотрит своё расписание, оценки, посещаемость, ДЗ и динамику пробных тестов. Ученики — несовершеннолетние, поэтому их данные защищаем особенно тщательно.

Регистрации нет. Единственная публичная страница — вход; роль определяется по учётной записи. Платформы: веб (адаптивный, устанавливаемый как PWA) и Android; iOS — позже, тот же код.

### Принципы работы

1. Права доступа и корректность данных важнее скорости. Любая проверка прав делается на сервере; фронтенд только прячет кнопки.
2. Работай по этапам из раздела «Этапы разработки». Этап закрыт, когда тесты зелёные, README обновлён, изменения закоммичены, а функцию можно показать на демо-данных.
3. В начале создай `CLAUDE.md` с соглашениями проекта (структура, команды, правила прав доступа) и `docs/decisions.md` — журнал решений в формате «дата · решение · почему».
4. Зависимостей — минимум. Каждую новую библиотеку обоснуй одной строкой в `docs/decisions.md`. Версии фиксируй lock-файлами.
5. Если требование неоднозначно и решение легко переделать — выбери самый простой вариант и запиши его. Если переделать дорого (схема БД, права, формулы оценок) — спроси меня.
6. Интерфейс — на русском, все строки вынесены в файлы перевода (чтобы потом добавить второй язык). Идентификаторы в коде — по-английски.

## 3. Стек и архитектура

Один бэкенд с REST API и один фронтенд, который работает как сайт, как PWA и как Android-приложение. Так три платформы живут на одной кодовой базе, а iOS потом добавляется сборкой, а не переписыванием.

```
[Браузер: сайт и PWA]   [Android: Capacitor]          [iPhone: PWA, iOS позже]
 cookie-сессия + CSRF    access + refresh в Keystore   cookie-сессия
          \                      |                          /
           +-------------------- HTTPS ---------------------+
                                 |
┌──────────────── Сервер · Docker Compose (наружу только 80 и 443) ────────────────┐
│  Caddy — HTTPS (Let’s Encrypt), HSTS, CSP и заголовки, статика фронтенда         │
│                                 |                                                │
│  Django + DRF · /api/v1 — вход, сессии, TOTP, лимиты; права: роль + for_user(),  │
│                           чужой объект → 404; аудит в той же транзакции          │
│          |                      |                                                │
│  Redis (сессии, лимиты,   PostgreSQL (данные,        <── cron (генерация занятий, │
│         кэш)               аудит только INSERT)            ночной бэкап)         │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Все три клиента ходят в один API через Caddy. Права, лимиты и аудит живут только на сервере, поэтому подмена запроса в браузере или приложении ничего не даёт.

**Бэкенд**

- Python 3.12+, Django (актуальная LTS) + Django REST Framework. Выбор из-за встроенной защиты: CSRF, ORM без SQL-инъекций, Argon2, security-middleware, миграции.
- PostgreSQL 16+ (без SQLite даже в разработке — нужны те же ограничения и триггеры, что в проде).
- Redis — сессии, лимиты запросов, кэш.
- `drf-spectacular` — OpenAPI-схема; из неё генерируется типизированный клиент для фронтенда (`openapi-typescript`).
- `pyotp` — TOTP; `openpyxl` + `defusedxml` — импорт/экспорт Excel; `Pillow` — перекодирование логотипа.
- Фоновые задачи (генерация занятий на 4 недели вперёд, очистка сессий, бэкап) — management-команды по cron в отдельном контейнере. Celery не нужен, пока нет уведомлений.
- Печатные формы (карточки доступа, ведомости, расписание) — HTML-страницы с print-стилями, без PDF-библиотек: PDF делает браузер.

**Фронтенд**

- React + TypeScript + Vite, React Router, TanStack Query.
- Radix UI — только нестилизованные примитивы (диалог, меню, поповер, селект) ради доступности. Готовые UI-киты в их дефолтном виде (MUI, Ant, shadcn) — нет.
- Стили — CSS Modules + дизайн-токены в CSS-переменных (раздел «Дизайн»). Формы — `react-hook-form` + `zod`.
- Графики — свои простые SVG-компоненты (линия динамики, столбцы), без тяжёлых библиотек.
- Шрифты и иконки (Lucide) — своим сервером, без CDN.
- PWA: `vite-plugin-pwa`; service worker кэширует только статику, ответы API — никогда.
- Мобильная сборка — Capacitor (Android сейчас, iOS позже), тот же код.

**Инфраструктура**

- Docker Compose: `caddy` (HTTPS через Let’s Encrypt, заголовки безопасности, раздача статики фронтенда), `api` (gunicorn), `db`, `redis`, `cron`. Наружу открыты только 80 и 443 у Caddy.
- Фронтенд на `/`, API на `/api/v1/` на одном домене: один origin, cookie без CORS.
- Отдельные настройки `dev` / `prod`, секреты только из `.env` (в репозитории — только `.env.example`).

**Структура репозитория**

```
backend/

  apps/accounts/     # пользователи, вход, сессии, 2FA
  apps/academics/    # годы, модули, предметы, группы, курсы, кабинеты
  apps/schedule/     # шаблон недели, занятия, исключения
  apps/journal/      # посещаемость, оценки, средние

  apps/reports/      # отчёты, экспорт
  apps/announcements/
  apps/audit/        # журнал аудита
frontend/
  src/app/           # роутинг, лэйауты по ролям
  src/features/      # auth, student, teacher, admin
  src/shared/ui/     # свои компоненты и токены
  src/shared/api/    # сгенерированный клиент
mobile/              # Capacitor-проект
infra/               # docker-compose, Caddyfile, скрипты бэкапа
docs/                # decisions.md, security.md, admin-guide.md
```

## 4. Вход, роли и инициалы в углу

Одна форма входа для всех: система сама понимает роль по учётной записи и открывает нужный раздел. Аккаунты создаёт только администратор.

### Форма входа

- Поля: «Логин», «Пароль» (с кнопкой «показать»), флажок «Запомнить это устройство» (для администратора не действует), кнопка «Войти».
- Под формой одна строка: «Нет доступа или забыли пароль? Обратитесь к администратору центра» + контакты из настроек. Ссылки «Зарегистрироваться» нет.
- Логин не чувствителен к регистру, пробелы по краям обрезаются.
- Любая ошибка — одинаковый текст «Неверный логин или пароль», чтобы нельзя было узнать, существует ли логин. При блокировке — «Слишком много попыток. Попробуйте через N минут», причём и для несуществующих логинов тоже.

### Как определяется роль

1. `POST /api/v1/auth/login` проверяет логин и пароль.
2. Если у учётной записи включена 2FA — ответ `{"step": "totp"}`, второй шаг — ввод 6-значного кода или резервного кода. Сессия создаётся только после него.
3. После входа `GET /api/v1/me` возвращает `{id, full_name, initials, roles, active_role, must_change_password}`.
4. Маршрут по роли: `admin` → `/admin`, `teacher` → `/teacher`, `student` → `/student`. Разделы чужой роли закрыты на сервере; на клиенте показывается 404.
5. Ролей у сотрудника может быть две (директор, который сам ведёт занятия): тогда открывается старшая, а в меню инициалов появляется переключатель роли. Роль «ученик» с другими не совмещается.

### Первый вход и пароли

- Логин генерируется из ФИО транслитерацией: «Алиев Фарход» → `aliev.f`, при совпадении — `aliev.f2`. Администратор может поправить.
- Временный пароль — 12 символов из алфавита без путающихся знаков (нет 0/O, 1/l/I), создаётся системой, показывается администратору один раз и печатается на карточке доступа. В БД — только хэш.
- При первом входе открывается только экран смены пароля; любой другой запрос к API отвечает 403 `password_change_required`.
- Новый пароль: не короче 10 символов, не из списка распространённых, не похож на логин и ФИО. Требований «заглавная + цифра + символ» нет — фраза из нескольких слов допустима. При вводе показывается простая шкала надёжности.
- Восстановление пароля — только через администратора: он выдаёт новый временный пароль, все сессии пользователя завершаются. Самостоятельного сброса по почте в первой версии нет.
- Администратор при первом входе обязан настроить TOTP (QR-код для Google Authenticator / Aegis) и получает 10 резервных кодов, показанных один раз. Преподаватель включает 2FA по желанию; администратор может сделать её обязательной для преподавателей.

### Инициалы в углу

- В правом верхнем углу шапки (на всех экранах и размерах) — кнопка-«штамп» 32×32 с двумя буквами: первая буква имени + первая буква фамилии (Фарход Алиев → «ФА»). Вид — в разделе «Дизайн».
- По клику — меню: ФИО, роль (и группы — для ученика), «Профиль», «Сменить пароль», «Активные сеансы», «Тема: светлая / тёмная / как в системе», переключатель роли (если есть), «Выйти». Меню управляется с клавиатуры.
- «Выйти» уничтожает сессию на сервере и очищает кэш запросов и кэши service worker на клиенте.
- «Активные сеансы»: устройство/браузер, примерное место по IP, время последней активности, кнопки «Завершить» и «Завершить все, кроме текущего».

## 5. Модель данных

Главная идея: **курс = группа + предмет + преподаватель**. Расписание, занятия, оценки и посещаемость висят на курсе. Ученик может состоять в нескольких группах (например, математика в одной, физика в другой) — для центров подготовки это обычное дело.

| Сущность | Ключевые поля | Ограничения и заметки |
| --- | --- | --- |
| `User` | id (UUID), login, password (Argon2id), last\_name, first\_name, middle\_name?, roles, is\_active, must\_change\_password, totp\_secret (зашифрован), last\_login\_at, archived\_at | login уникален без учёта регистра |
| `StudentProfile` | user, phone?, school, school\_grade (9/10/11), target (вуз/направление), target\_score?, parent\_name?, parent\_phone?, admin\_note | контакты родителей и admin\_note видит только администратор |
| `TeacherProfile` | user, phone?, subjects |  |
| `AcademicYear`, `Term` | name, starts\_on, ends\_on, is\_current; модули внутри года | модули не пересекаются |
| `Subject` | name, short\_name (3–6 букв) |  |
| `Room` | name, capacity |  |
| `Group` | name («11-М вечерняя»), academic\_year, level, is\_archived |  |
| `GroupMembership` | group, student, joined\_on, left\_on? | история состава; периоды одного ученика в одной группе не пересекаются |
| `Course` | group, subject, teacher, assistants? | unique(group, subject) |
| `LessonType` (справочник) | name, short («Лк», «Пр», «КР»), default\_work\_type, counts\_attendance | по умолчанию: лекция, практика, семинар, контрольная, пробный тест, консультация, повторение |
| `WorkType` (справочник) | name, weight | ответ на занятии ×1, ДЗ ×1, самостоятельная ×1.5, контрольная ×2 |
| `ScheduleSlot` | course, weekday, start\_time, end\_time, room, valid\_from, valid\_to | шаблон недели |
| `Lesson` | course, date, start\_time, end\_time, room, teacher (фактический), lesson\_type, topic, homework, status (planned / conducted / cancelled), cancel\_reason, slot?, version | teacher может отличаться от текущего преподавателя курса (замена) |
| `Attendance` | lesson, student, status (present / late / absent / excused), late\_minutes?, comment, marked\_by | unique(lesson, student) |
| `Grade` | lesson, student, value, work\_type, weight (копируется при создании), comment?, created\_by, deleted\_at | CHECK на диапазон шкалы; до 3 на ученика за занятие; удаление мягкое |
| `Exam`, `ExamSection`, `ExamResult` | тест: title, subject, courses, date, max\_score; разделы: name, max\_score; результат: student, total, section\_scores, was\_absent | сумма разделов = total |
| `TeacherNote` | student, course, author, text | видят автор и администратор, ученик — никогда |
| `Announcement` | author, title, body (простой текст), audience (все / роль / группы), pinned, published\_at, expires\_at |  |
| `Holiday` | date, name | занятия не генерируются |
| `AuditLog` | at, actor, ip, user\_agent, action, entity\_type, entity\_id, before (JSON), after (JSON), reason? | только добавление: триггер в PostgreSQL запрещает UPDATE и DELETE |
| `LoginEvent` | at, login\_attempted, user?, ip, user\_agent, success, reason |  |
| `UserSession` | user, key\_hash, created\_at, last\_seen\_at, ip, user\_agent, remember | для списка сеансов и отзыва |
| `Settings` | одна запись: название, логотип, контакты, шкала, окно редактирования, пороги, тайм-ауты, политика 2FA | изменения пишутся в аудит |

**Формулы** (одна функция на сервере, её используют все экраны и отчёты):

- Средневзвешенный балл = Σ(оценка × вес) / Σ(вес) по неудалённым оценкам за период, округление до 2 знаков.
- Посещаемость, % = (присутствовал + опоздал) / (проведённые занятия, где ученик был в группе и вид занятия учитывает посещаемость, − пропуски по уважительной причине) × 100. Уважительные пропуски показываются отдельным числом.
- Все метки времени хранятся в UTC, отображаются в часовом поясе центра.

## 6. Ученик

Ученик только смотрит — менять он может лишь пароль, тему оформления и свои сеансы. Данные других учеников ему недоступны нигде, включая рейтинги (место в группе выключено в настройках по умолчанию).

Навигация: на компьютере — текстовые вкладки в шапке, на телефоне — нижняя панель из 5 пунктов: Главная · Дневник · Оценки · Тесты · Расписание. Посещаемость и профиль — из главной и из меню инициалов.

1. **Главная.** Занятия на сегодня (время, предмет, кабинет, преподаватель, пометки «замена» / «перенесено» / «отменено»). Новые оценки за 7 дней. ДЗ к ближайшим занятиям. Компактная таблица «предмет · средний балл · посещаемость». Закреплённые объявления.
2. **Дневник.** Неделя как разворот бумажного дневника: по дням — занятия, вид занятия, тема, ДЗ, оценки, отметки «н» / «оп». Листание недель стрелками и свайпом, кнопка «Сегодня».
3. **Оценки.** Выбор периода (модуль / год). Таблица «предметы × даты», в конце строки — средневзвешенный балл. Клик по оценке — дата, тема, вид работы, вес, комментарий преподавателя. На телефоне — список предметов, внутри — список оценок по датам.
4. **Пробные тесты.** График динамики балла по каждому предмету с пунктирной линией цели (target\_score). Таблица тестов: дата, название, балл / максимум, изменение к прошлому. Разбивка по разделам — видно, где теряются баллы.
5. **Посещаемость.** Процент по каждому предмету и в целом; календарь месяца с отметками пропусков и опозданий.
6. **Расписание.** Неделя сеткой (дни × время) на компьютере, списком по дням на телефоне. Изменения помечены.
7. **Профиль.** ФИО, группы, цель (вуз и балл — заполняет администратор), смена пароля, активные сеансы, тема.

## 7. Преподаватель

Главное для преподавателя — заполнить занятие за минуту с телефона прямо в аудитории. Преподаватель видит только свои курсы и занятия, где он стоит заменой.

1. **Сегодня** (главная). Занятия дня строками: время, группа, предмет, кабинет, статус «впереди / нужно заполнить / заполнено». Блок «Не заполнено» — прошедшие занятия без темы или посещаемости. Блок «Внимание» — ученики с посещаемостью ниже порога или двумя низкими оценками подряд.
2. **Страница занятия** — главный рабочий экран.
   - Шапка: дата, время, группа, предмет, кабинет.
   - Поля: вид занятия (список), тема (обязательна, чтобы закрыть занятие; есть подсказки из прошлых тем курса), ДЗ (текст и ссылки), комментарий.
   - Список учеников, состоявших в группе на дату занятия. У каждого: переключатель посещаемости (по умолчанию «был»; тап циклит: был → опоздал → отсутствовал → уважительная; на компьютере — клавиши Б / О / Н / У), до трёх оценок с видом работы, значок комментария.
   - Оценка на телефоне — цифровая клавиатура (inputmode="numeric") с проверкой диапазона 0–100 прямо при вводе. Для 5- и 10-балльной шкалы — нижняя панель с крупными кнопками значений.
   - Кнопки: «Все присутствуют», «Завершить занятие». Изменения сохраняются сразу, статус текстом: «Сохранено · 14:32» или «Не сохранено — повторить». Отмена последнего действия — 10 секунд.
   - При статусе «отсутствовал» поле оценки неактивно.
3. **Журнал** (сетка). Выбор курса и периода.
   - Строки — ученики («Алиев Ф.»), колонки — занятия (дата + сокращение вида занятия, тема во всплывающей подсказке). Справа — средневзвешенный балл, посещаемость %, число пропусков.
   - Первая колонка и строка дат закреплены при прокрутке.
   - Клавиатура: стрелки — переход по ячейкам, число + Enter — оценка, «н» — отсутствие, Delete — удалить, Enter — подробности, Esc — выход.
   - Ячейки за пределами окна редактирования заблокированы, подсказка: «Изменить может администратор».
   - Вкладка «Темы» — как правая страница бумажного журнала: дата, вид занятия, тема, ДЗ по каждому занятию.
   - На телефоне сетка прокручивается горизонтально с закреплёнными именами, а редактирование идёт через страницу занятия.
4. **Мои группы.** Состав каждого курса; карточка ученика по своему предмету: оценки, посещаемость, тесты, личная заметка преподавателя. Телефоны родителей преподаватель не видит.
5. **Расписание.** Моя неделя, замены и переносы помечены.
6. **Пробные тесты.** Создать тест для своих курсов (название, дата, максимум, разделы), внести баллы таблицей или импортом из Excel, увидеть среднее, медиану и распределение.
7. **Отчёты.** Ведомость по своему курсу за период → XLSX и печать.

## 8. Администратор

Администратор управляет всем центром через собственный интерфейс; встроенная админка Django в проде выключена. Навигация — узкая левая колонка с текстовым списком разделов.

1. **Обзор.** Занятия сегодня (всего / проведено / не заполнено). Незаполненные занятия старше 2 дней — сгруппированы по преподавателям. Ученики ниже порога посещаемости. Заблокированные входы. Последние 20 событий аудита. Каждый блок ведёт к действию, а не просто показывает число.
2. **Пользователи.**
   - Таблица с поиском и фильтрами (роль, группа, активен / в архиве); создание и редактирование.
   - Импорт из CSV/XLSX по шаблону: предпросмотр с ошибками по строкам до записи, потом одна транзакция. Логины и временные пароли генерируются.
   - **Карточки доступа**: печатный лист A4 по 8 карточек (ФИО, логин, временный пароль, адрес сайта, QR-код с адресом). Пароль доступен для печати один раз, потом — только сброс.
   - Сброс пароля, блокировка / разблокировка, архивация, список и завершение сеансов, сброс 2FA.
3. **Группы.** Создание, состав (добавить / перевести / исключить — с датой), курсы группы (предмет + преподаватель).
4. **Справочники.** Предметы, кабинеты, виды занятий, виды работ и их веса, нерабочие дни, учебные годы и модули.
5. **Расписание** — конструктор, раздел 9.
6. **Журналы.** Просмотр любого курса. Правка за пределами окна редактирования — только с обязательной причиной, которая попадает в аудит.
7. **Пробные тесты.** Все тесты, сравнение групп по одному тесту, динамика по центру.
8. **Отчёты.** Успеваемость и посещаемость по группе / предмету / периоду; заполняемость журналов по преподавателям; сводная ведомость ученика для родителей (печать на одном листе). Экспорт XLSX / CSV.
9. **Объявления.** Для всех, для роли или для групп; закрепление и срок показа.
10. **Аудит.** Фильтры по пользователю, действию, сущности и датам; вид «было → стало»; экспорт. Отдельная вкладка — журнал входов.
11. **Настройки.** Всё из раздела 2 + статус последнего бэкапа.

Опасные действия — смена ролей, сброс 2FA, массовая архивация, изменение шкалы, экспорт персональных данных — требуют повторного ввода пароля, если последний ввод был больше 5 минут назад.

## 9. Расписание

Расписание строится из шаблона недели, из него система сама создаёт конкретные занятия, а все разовые изменения — исключения поверх него.

- **Шаблон недели.** Для каждого курса — слоты: день недели, начало, конец, кабинет, период действия. Редактор — сетка «дни × время» с фильтром по группе, преподавателю или кабинету; слот добавляется и правится формой. Перетаскивание — не в первой версии.
- **Генерация занятий.** Каждую ночь — на 4 недели вперёд, идемпотентно (повторный запуск не создаёт дублей), пропуская нерабочие дни. Изменение шаблона применяется только к будущим непроведённым занятиям и после подтверждения со списком затронутых дат.
- **Исключения** (делает администратор): отмена с причиной; перенос на другую дату, время или кабинет; замена преподавателя на одно занятие; разовое дополнительное занятие (консультация, пробный тест). Преподаватель может отправить администратору запрос на отмену или перенос.
- **Конфликты** проверяются на сервере при каждом сохранении. Пересечение по преподавателю, кабинету или группе — блокирует сохранение и показывает, с чем именно конфликт. Пересечение у ученика из двух групп — предупреждение со списком учеников. Превышение вместимости кабинета — предупреждение.
- **Представления.** По группе, преподавателю, кабинету, ученику; день и неделя. Печать расписания группы на A4 альбомной ориентации.
- Ученики и преподаватели видят изменения с пометками «отменено», «перенесено с …», «замена: …»; отменённое занятие остаётся видно зачёркнутым.

## 10. Бизнес-правила

Каждое правило проверяется на сервере и покрыто тестом; интерфейс лишь не даёт нажать то, что сервер всё равно отклонит.

1. Преподаватель пишет посещаемость, оценки и темы только в занятия своих курсов или в занятия, где он назначен заменой.
2. Оценки и посещаемость — только для занятий с датой не позже сегодняшней (в часовом поясе центра) и не отменённых.
3. Оценку и отметку можно поставить только ученику, который состоял в группе на дату занятия.
4. Преподаватель меняет и удаляет свои записи в течение окна редактирования (7 дней от даты занятия). Потом — только администратор и только с причиной (без причины — 400).
5. Занятие можно пометить проведённым, когда заполнены тема, вид занятия и посещаемость каждого ученика. Оценки необязательны.
6. Не больше 3 оценок на ученика за занятие; у каждой — вид работы и вес. Отсутствовавшему оценку в это занятие поставить нельзя; за пропущенную контрольную оценка ставится на занятии, где её переписали.
7. Удаление оценки — мягкое: она исчезает из журнала и средних, но остаётся в аудите.
8. Любое изменение оценки, посещаемости, темы, состава группы, ролей и настроек пишется в аудит в той же транзакции, что и само изменение.
9. Перевод ученика в другую группу закрывает старое членство датой и открывает новое. Старые оценки остаются в старом курсе и видны ученику в истории.
10. Архивация пользователя отключает вход и завершает сеансы, данные сохраняются. Физического удаления пользователей с оценками нет.
11. Шкалу оценок нельзя поменять для учебного года, в котором уже есть оценки.
12. Два человека правят одно занятие — оптимистичная блокировка по `version`: второй получает 409 и сообщение «Запись изменена другим пользователем, обновите страницу».
13. Средние баллы и проценты считает только сервер, одной функцией для всех экранов и отчётов — чтобы цифры везде совпадали.

## 11. Безопасность

Цель — уровень OWASP ASVS 2: чтобы ученик не мог исправить себе оценку, не увидел чужие данные и не подобрал пароль учителя. Самая частая дыра в таких системах — подмена ID в запросе (IDOR), поэтому права на объекты — первый приоритет.

### Аутентификация

- Пароли — Argon2id (первый в `PASSWORD_HASHERS`), валидаторы Django: длина ≥ 10, список распространённых, сходство с атрибутами пользователя.
- Лимиты на вход (Redis): по логину — 5 неудач → блокировка с растущим сроком; по IP — 20 попыток за 10 минут. Ответ и время ответа одинаковы для существующего и несуществующего логина (для несуществующего хэшируем пустышку).
- Сессии серверные. Cookie `__Host-session`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. Идентификатор сессии меняется при входе, смене пароля и роли. Тайм-ауты бездействия и абсолютные — по роли (раздел 2). Смена пароля завершает все остальные сеансы.
- CSRF-защита Django на всех изменяющих запросах (токен в заголовке `X-CSRFToken`), `CSRF_TRUSTED_ORIGINS` — только свой домен.
- TOTP-секреты шифруются ключом из `.env`; резервные коды хранятся хэшами и одноразовы; на ввод кода — свой лимит попыток.
- Мобильный клиент: access-токен на 10 минут только в памяти + refresh-токен на 30 дней в Android Keystore (secure storage). Refresh ротируется при каждом использовании; повторное использование старого отзывает всю цепочку. Токены никогда не лежат в `localStorage`.

### Авторизация

- Запрет по умолчанию: у каждого view — явные permission-классы. Тест обходит все URL и падает, если где-то стоит `AllowAny` (кроме `/auth/login` и `/health`).
- Права на объекты через queryset: метод `for_user(user)` у каждого менеджера (ученик — только своё, преподаватель — только свои курсы и замены). Объект вне области видимости — 404, а не 403, чтобы не выдавать факт существования.
- Сериалайзеры с явным списком полей (никакого `__all__`), отдельные для каждой роли. `roles`, `is_active`, `created_by` и подобные поля нельзя передать через API, кроме админских эндпоинтов.
- Матрица прав «роль × действие × чей объект» лежит в `docs/security.md` и проверяется параметризованными тестами (раздел 15).

### Данные и ввод

- Только ORM; сырой SQL — только с параметрами и с обоснованием в `docs/decisions.md`.
- Валидация на сервере сериалайзерами и CHECK-ограничениями в БД; клиентская валидация — только для удобства.
- Во фронтенде нет `dangerouslySetInnerHTML`. Текст объявлений, тем и ДЗ — простой текст с автоссылками (только `https://`, `rel="noopener noreferrer"`).
- Загрузки: логотип до 1 МБ, импорт до 5 МБ; проверка реального типа файла; логотип перекодируется в PNG без метаданных; файлы — вне webroot со случайными именами. XLSX читается в read-only режиме с `defusedxml`.
- Экспорт CSV/XLSX экранирует ячейки, начинающиеся с `=`, `+`, `-`, `@` (защита от формул-инъекций).
- Минимум персональных данных детей. В логах нет паролей, токенов, cookie и телефонов.
- Таблица аудита защищена триггером от UPDATE/DELETE; приложение работает под пользователем БД без прав суперпользователя.

### HTTP и сервер

- Только HTTPS, HSTS на 1 год, редирект с HTTP.
- Заголовки (ставит Caddy):

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none';
  base-uri 'none'; form-action 'self'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
Cross-Origin-Opener-Policy: same-origin
```

- Никаких inline-скриптов и внешних CDN. Сервис воркер не кэширует `/api/`, при выходе кэши очищаются.
- `DEBUG=False`, свои страницы ошибок без стектрейсов; `manage.py check --deploy` без предупреждений.
- Общий лимит API — 300 запросов в минуту на пользователя, экспорт и импорт — строже.
- Контейнеры от не-root пользователя; PostgreSQL и Redis не открыты наружу, Redis с паролем.
- Сервер: вход по SSH только по ключу, root отключён, фаервол только 22/80/443, fail2ban, автообновления безопасности. Инструкция — в `docs/deploy.md`.
- Бэкапы: еженочный `pg_dump`, зашифрованный (age), хранится вне сервера: 14 ежедневных, 8 еженедельных, 12 ежемесячных. Скрипт проверки восстановления запускается раз в месяц.
- Зависимости зафиксированы; в CI — `pip-audit`, `npm audit`, `bandit`, Dependabot.
- Мониторинг: структурные логи; администратор видит в обзоре блокировки, всплески отказов в доступе и входы администраторов с новых устройств.
- Перед релизом — OWASP ZAP baseline по тестовому стенду, отчёт в `docs/security.md`.

## 12. Дизайн

Концепция — **«Журнал, а не дэшборд»**: визуальный язык бумажного классного журнала и тетради, переведённый в точный экранный инструмент. Разлиновка вместо карточек, чернила вместо градиентов, плотные таблицы вместо плиток со статистикой, жёсткие границы и моноширинные цифры. Интерфейс должен выглядеть как сделанный руками для этого центра, а не собранный из шаблона.

Первой задачей фронтенда сделай страницу `/dev/styleguide` (только в dev): цвета, шрифты, кнопки, поля, таблица, ячейки журнала, штамп инициалов в светлой и тёмной теме. Экраны собираются только из этих компонентов.

### Цвета

| Токен | Светлая «Бумага» | Тёмная «Ночная тетрадь» | Зачем |
| --- | --- | --- | --- |
| `--paper` | `#F4F1E8` | `#13161B` | фон страницы |
| `--sheet` | `#FBFAF5` | `#1A1E25` | поверхность таблиц и форм |
| `--ink` | `#1B2130` | `#E9E5DA` | основной текст, рамки ключевых элементов |
| `--ink-2` | `#5A6170` | `#9BA1AB` | вторичный текст, подписи |
| `--rule` | `#DAD4C5` | `#2B313B` | линии разлиновки таблиц |
| `--accent` | `#2340A0` | `#8EA6FF` | синие чернила: ссылки, фокус, активный пункт, выбранная ячейка |
| `--red-pen` | `#BF3328` | `#FF6E61` | красная ручка: «н», низкие оценки, ошибки, линия полей |
| `--pencil` | `#A86F12` | `#E0A94A` | опоздания, предупреждения |
| `--marker` | `#FFE24A` | `#E5CF3E` (прозрачность 35%) | жёлтый текстовыделитель — ТОЛЬКО сегодняшний день и совпадения поиска |

Зелёного «успеха» нет: хорошие оценки пишутся обычными чернилами, красным — только то, что требует внимания. Цвет никогда не единственный сигнал: у пропуска есть буква «н», у опоздания — «оп». Если у центра есть фирменный цвет — он заменяет `--accent`, остальное не меняется. Контраст текста — не ниже WCAG AA, проверь скриптом.

### Шрифты (все с кириллицей, OFL, своим сервером)

- **Literata** 600 — заголовки страниц, название центра, ФИО в карточке ученика. Книжная антиква даёт ощущение журнала.
- **Golos Text** 400/500/600 — весь интерфейс. Рисовался под кириллицу и экраны.
- **JetBrains Mono** 500/700 — оценки, баллы, время, даты в сетке, логины, инициалы в штампе.
- Шкала: 12 / 14 / 15 (база на компьютере) / 16 (база на телефоне) / 20 / 28 / 40. Межстрочный интервал текста 1.45. Везде, где есть цифры в столбце, — `font-variant-numeric: tabular-nums`.

### Форма и компоненты

- Сетка отступов — шаг 8 px. Скругления 0–2 px. Мягких теней нет: глубина — через линии 1 px и разницу `--paper` / `--sheet`.
- Одна фирменная деталь — жёсткая тень `3px 3px 0 var(--ink)` и рамка 1.5 px: только у модальных окон и главной кнопки на экране.
- Кнопки: главная — заливка `--ink`, текст `--paper`; вторичная — рамка 1 px; опасная — рамка и текст `--red-pen`. Текст со строчной буквы, не капсом.
- Поля ввода — как строка в тетради: только нижняя линия 1.5 px, подпись сверху 12 px `--ink-2`. Фокус — линия `--accent` 2 px + видимый outline для клавиатуры.
- **Сетка журнала** — главный экран продукта: тонкая разлиновка `--rule`; колонку с фамилиями отделяет вертикальная линия `--red-pen`, как поля в тетради; колонка сегодняшнего дня подсвечена маркером; оценки — JetBrains Mono 15/700, ширина ячейки рассчитана на трёхзначные баллы; граница недели — линия потолще; при наведении подсвечиваются строка и столбец; высота строки 36 px (на телефоне 44 px — цель для пальца).
- **Штамп инициалов** — квадрат 32×32, рамка 1.5 px, две буквы JetBrains Mono 13/700, лёгкая заливка 10%. Цвет рамки и букв — из 6 приглушённых чернильных оттенков, выбирается по хэшу id пользователя. Не кружок.
- Навигация: слева в шапке — название центра (Literata), дальше текстовые вкладки с подчёркиванием активной, справа — штамп. На телефоне — нижняя панель: тонкие иконки с подписями.
- Иконки — Lucide с линией 1.5 px, только где несут смысл (замок, предупреждение, стрелки недели).
- Графики — тонкая линия `--ink`, точки с подписанными баллами, цель — пунктир `--accent`. Без заливки под линией и градиентов.
- Загрузка — скелетон в виде пустой разлиновки, а не спиннер. Пустое состояние — одна строка текста и действие («На сегодня занятий нет.»), без иллюстраций.
- Анимации 120–160 мс, только opacity и transform, уважать `prefers-reduced-motion`.
- Тексты интерфейса — короткие и деловые, без восклицаний и эмодзи. Даты человеческие: «пт, 21 ноября».

### Страница входа

Фон `--paper`, узкая колонка 360 px по центру. Сверху — строка в JetBrains Mono, как шапка журнальной страницы: «21.11.2026 · пятница». Дальше название центра (Literata 28), подпись «Электронный журнал», форма, строка помощи. Без картинок, слоганов и половины экрана с иллюстрацией.

### Запрещено (признаки шаблонного «ИИ-дизайна»)

- фиолетово-синие градиенты, градиентный текст, «стекло» (glassmorphism), неон и свечение;
- скругления 12–24 px и карточки с мягкими тенями на всё подряд;
- ряд из четырёх KPI-плиток с иконками в цветных кружках вверху экрана;
- эмодзи, маскоты, 3D-иллюстрации, иконка «искорки»;
- Inter или системный шрифт по умолчанию; текст капсом;
- UI-киты в дефолтной теме;
- параллакс, конфетти, «прыгающие» анимации;
- маркетинговые фразы вроде «Добро пожаловать в будущее образования!».

### Адаптивность и доступность

Точки перелома: 360–599 (телефон), 600–1023 (планшет), ≥ 1024 (компьютер). WCAG 2.2 AA: всё доступно с клавиатуры, фокус виден, у иконок-кнопок есть aria-label, цели нажатия на телефоне ≥ 44 px.

## 13. Android сейчас, iPhone — без лицензии

Итог: веб и Android делаем сразу, а владельцы iPhone пользуются PWA — ей не нужен аккаунт Apple Developer. Нативная iOS-сборка появится, когда будет лицензия, из того же кода.

- **PWA.** Manifest (название, иконки 192/512 и maskable, `theme_color` = `--paper`), установка на Android и на iPhone через Safari → «На экран Домой». На странице входа для iPhone — короткая подсказка, как установить. Офлайн — только оболочка и страница «Нет соединения», данные не кэшируются.
- **Android (Capacitor).** Проект в `mobile/`, приложение грузит собранный фронтенд из себя (не удалённый URL), к API ходит по HTTPS с токенами (раздел 11). Слой `platform/` абстрагирует хранение токена и системную кнопку «Назад», чтобы вебу и iOS не мешали Android-специфичные вызовы.
- **Безопасность сборки:** отладка WebView выключена в release, `android:allowBackup="false"`, cleartext-трафик запрещён в network security config, ключ подписи — вне репозитория.
- **Распространение:** сначала APK напрямую сотрудникам и ученикам; потом Google Play. Проверь актуальные требования Play к новым личным аккаунтам (закрытое тестирование перед публикацией) и верификации разработчиков.
- **iOS позже:** `npx cap add ios`, сборка на macOS в Xcode, подпись аккаунтом Apple Developer. Токен — в Keychain через тот же слой `platform/`.

## 14. Этапы разработки

Каждый этап заканчивается работающим результатом на демо-данных; после каждого — остановись и покажи, что сделано. Начиная с этапа 1 команда `manage.py seed_demo` создаёт 1 администратора, 6 преподавателей, 4 группы, 60 учеников и 8 недель занятий с оценками и посещаемостью; пароли печатает в консоль, в production отказывается запускаться.

0. **Фундамент.** Структура репозитория, Docker Compose для разработки, ruff + mypy, eslint + prettier, pre-commit, CI (тесты, линтеры, `pip-audit`, `npm audit`, `bandit`), `CLAUDE.md`, `docs/decisions.md`, дизайн-токены, шрифты и `/dev/styleguide`.
1. **Вход и пользователи.** Модели пользователей и профилей; вход с определением роли; смена временного пароля; сессии и их список; лимиты и блокировки; TOTP для администратора; аудит и журнал входов; CRUD пользователей; шапка со штампом инициалов и меню; тесты входа из раздела 15.
2. **Структура и расписание.** Годы и модули, предметы, кабинеты, группы и составы, курсы, справочники; шаблон недели, генерация занятий, исключения, конфликты; расписание для всех ролей.
3. **Журнал.** Страница занятия, сетка с клавиатурным вводом, вкладка тем, окно редактирования, аудит изменений, средние и посещаемость, главная преподавателя.
4. **Кабинет ученика.** Главная, дневник, оценки, посещаемость, расписание, профиль.
5. **Администрирование и аналитика.** Пробные тесты, объявления, отчёты и экспорт, импорт из Excel, карточки доступа, обзор администратора, экран аудита, настройки.
6. **PWA и Android.** Manifest, service worker, токены для мобильного клиента, Capacitor, сборка подписанного APK.
7. **Продакшен.** Caddy и HTTPS, заголовки, бэкапы и проверка восстановления, hardening сервера, мониторинг, ZAP-скан, `docs/deploy.md` и `docs/admin-guide.md` (как начать учебный год: группы → импорт учеников → карточки → расписание).

## 15. Критерии готовности и тесты

Работа считается сделанной, когда всё ниже проходит в CI, а не когда «вроде работает».

**Тесты прав доступа** (pytest, параметризованная матрица «эндпоинт × роль × чей объект»). Обязательные случаи:

- ученик A запрашивает оценки ученика B по ID → 404;
- ученик пытается изменить свою оценку или посещаемость → 403;
- преподаватель ставит оценку в чужом курсе → 404; в занятии, где он замена → 201;
- преподаватель меняет оценку старше окна → 403; администратор без причины → 400, с причиной → 200 и запись в аудите;
- оценка ученику, которого не было в группе на дату занятия, или за будущее занятие → 400;
- неаутентифицированный запрос к любому `/api/` кроме входа и `/health` → 401;
- пользователь с временным паролем запрашивает что-то кроме смены пароля → 403;
- 6-я неверная попытка входа → 429, и ответ для несуществующего логина байт-в-байт такой же;
- запрос без CSRF-токена → 403; cookie сессии имеет флаги `HttpOnly`, `Secure`, `SameSite`;
- все URL имеют проверку прав (тест-обходчик);
- попытка UPDATE/DELETE в таблице аудита падает на уровне БД.

**Тесты логики:** формулы среднего и посещаемости на краевых случаях (нет оценок, только уважительные пропуски, перевод между группами), конфликты расписания, идемпотентность генерации занятий, оптимистичная блокировка, часовой пояс на границе суток.

**Фронтенд:** Vitest + Testing Library для сетки журнала и форм; Playwright e2e — вход каждой ролью ведёт на свою страницу; преподаватель заполняет занятие → ученик видит оценку; принудительная смена пароля; импорт учеников администратором.

**Числа, которые надо выдержать:**

- покрытие модулей `accounts` и `journal` ≥ 85%;
- API сетки журнала для 35 учеников × 60 занятий — быстрее 500 мс, число SQL-запросов не растёт с числом строк (тест на N+1);
- `manage.py check --deploy` — без предупреждений; Mozilla Observatory — A+;
- Lighthouse: Accessibility ≥ 95, Performance ≥ 90 на странице входа и главной ученика.

**Документация:** README (запуск за 5 команд), `docs/security.md` (матрица прав и краткая модель угроз), `docs/deploy.md`, `docs/admin-guide.md`, OpenAPI-схема на `/api/v1/schema/` (только для администратора в проде).

## 16. На потом и открытые вопросы

Это не делать сейчас, но архитектура не должна этому мешать. Список отсортирован по пользе для центра подготовки.

1. **Роль «Родитель»** — доступ только к своим детям: оценки, посещаемость, пробные тесты. Для центра, где платят родители, это обычно самая востребованная функция. Заложи связь `ParentLink(parent, student)` и роль в модели сразу.
2. **Telegram-бот уведомлений** — пропуск, новая оценка, отмена занятия, результат пробного теста. Привязка аккаунта одноразовым кодом из профиля.
3. **Оплаты и абонементы** — учёт оплат по курсам, долги, напоминания.
4. **Онлайн-пробники** — банк вопросов, тестирование в формате вступительного экзамена с автопроверкой и таймером.
5. **Отзыв преподавателя раз в модуль** — 2–3 предложения о сильных и слабых сторонах ученика, попадает в сводную ведомость для родителей.
6. **Офлайн-режим для преподавателя** — очередь изменений при плохом интернете с синхронизацией и разрешением конфликтов.
7. **Подписка на расписание в календарь** (iCal) по личной ссылке с секретным токеном и кнопкой перевыпуска.
8. **Второй язык интерфейса.**
9. **Заявки новых учеников** — простая воронка набора (заявка → пробное занятие → зачисление).
10. **iOS-приложение** — когда появится лицензия Apple Developer.

**Открытые вопросы** (до ответа — работать с указанным вариантом):

- Группа — это «класс» со всеми предметами или отдельная группа на каждый предмет? Модель поддерживает оба; по умолчанию интерфейс строится вокруг группы с несколькими курсами.
- Где будет хостинг: арендованный VPS или сервер в самом центре? По умолчанию — VPS с Ubuntu LTS, 2 vCPU / 4 ГБ.
- Нужны ли дробные баллы (например, 87.5)? По умолчанию — нет, только целые от 0 до 100.
